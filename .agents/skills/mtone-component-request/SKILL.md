# mtone 组件需求交接

## 输入与边界

读取 [UI 指南](../../../docs/development/ui-mtone.md) 和 [ADR 0002](../../../docs/decisions/0002-mtone-ui-ownership.md)。输入消费任务、用户场景、实际锁定版本及公开能力证据。没有版本/证据时写“未取得”，不能推断缺组件。

Knoted 只做业务组合/数据适配；Agent 只读核查 mtone，不修改其仓库、不代建上游 Issue/PR、不发布 npm。不在本仓库复制/patch/包装 Base UI 补通用能力，不创建 @knoted/ui 转发层。正式交付使用已发布 npm，不以 link/Git/未发布 tarball 解阻塞。

## 执行步骤

1. 查实际 package/lock 与该发布版本的 exports、types、文档和 CSS；区别发布包与 master。将**亲自验证、输入事实、建议、未知**分开。读取失败就输出待核查项，不能捏造验证结果。
2. 搜索[已有需求记录](../../../docs/plans/knoted-v1/mtone-requests/README.md)与关联 Knoted Issue，识别同一能力/消费场景；重复需求补充原记录。未能查重就标明，不能声称无重复。
3. 分类：

   | 结果 | 交付 |
   |---|---|
   | 已有组件可用 | 指明实际公开组件与消费测试，不提新组件 |
   | 现有组件能组合/纯业务适配 | 说明 Knoted 的组合与状态责任，不提通用库任务 |
   | 资料不足/尚未实验 | 列待核查资料与最小验证步骤，不发布“确定缺失”结论 |
   | 已证实通用缺口 | 生成下列完整提示词，直接发给用户并存档 |

4. 不用“无同名导出”代替能力判断。API 只有 items/next_cursor 时先用已有 Button 组合翻页，不能为了 Pagination 伪造 total。业务权限、API、DTO、编辑器命令不进入 mtone。
5. 真实缺口使用下方输出契约；证据附件缺失时保留明确待补项，不能把输入断言写成亲自复现。
6. 记录关联任务的受影响验收与恢复条件。等待上游用技术依赖 blocked，保留 Projects 阶段；没有新增架构/权限边界不标 human-required。仅已交接不算完成。用户返回 npm 版本后核验发布、精确锁版、消费测试及正常 PR/主线/适用部署收尾，才解除相应依赖并完成任务。

## 输出契约

先给分类结论与理由；真实缺口再输出**一个完整可复制的提示词**，以下各槽位必填，未知明确写未提供：

1. **身份与状态**：需求 ID、关联消费任务/Issue、查重结论、存档路径；区分草稿/已交用户/待发布/待消费验收/已验证。
2. **版本与证据**：实际 npm 锁定版本、资料 URL/文件/行号、复现步骤及结果；输入事实和亲测分开，缺失证据列待补。
3. **目标与非目标**：可跨应用复用的能力，排除 Knoted 后端、DTO、权限及编辑器业务。
4. **公开接口建议**：现有 API、无法组合满足的理由、拟增能力分别写；props 名只是提案，由 mtone 开发者确认，兼容旧用法。
5. **状态与交互**：受控/非受控（按需）、键盘、焦点、无障碍、加载/禁用/错误/取消及生命周期；不适用项写原因。
6. **验收与交付**：可复现用例、上游测试/类型/文档/最小消费示例、实际结果、变更说明与包含修复的 npm 发布版本，不指定未经核实的上游命令。
7. **消费端恢复**：哪些任务等待、何种已发布版本/公开能力可恢复、Knoted 哪些测试与集成必须通过；master 合入不等于可消费。

提示词之外附本地下一步和未验证项。存档遵守独立 Worktree；用户收到提示词才标已交接，不能仅写文件或创建 Knoted Issue 就声称已交用户。

## 判定示例与常见错误

T19 仅有 next_cursor、没有 total，但 mtone 有 Button：结论是现有组件组合，游标栈留在 Knoted；输出下一页/上一页/筛选重置验收，不申请 PagedList，不造总数。

- “文档未读到” → 待核查，不是已确认缺失。
- “同事说 master 修了” → 输入事实、待发布，不跳过消费验收。
- “赶进度先写本地通用实现” → 记录技术依赖与上游交接，保留已有未合入成果，不擅自删除，也不合入替代库。
- “已有组件叫 Modal，不叫 Dialog” → 按真实 API 验证，不要求别名层。
