# mtone 组件需求交接

## 输入与边界

读取 [UI 指南](../../../docs/development/ui-mtone.md) 和 [ADR 0002](../../../docs/decisions/0002-mtone-ui-ownership.md)。输入消费任务、用户场景、实际锁定版本及公开能力证据。没有版本/证据时写“未取得”，不能推断缺组件。

Knoted 只做业务组合/数据适配；Agent 只读核查 mtone 源码与发布包，不修改其源码或提交 PR，不发布 npm；除按步骤 6 创建上游 Issue 或在已存在的同能力 Issue 下补充评论外，不写其仓库。不在本仓库复制/patch/包装 Base UI 补通用能力，不创建 @knoted/ui 转发层。正式交付使用已发布 npm，不以 link/Git/未发布 tarball 解阻塞。

## 执行步骤

1. 查实际 package/lock 与该发布版本的 exports、types、文档和 CSS；区别发布包与 master。将**亲自验证、输入事实、建议、未知**分开。读取失败就输出待核查项，不能捏造验证结果。
2. 搜索[已有需求记录](../../../docs/plans/knoted-v1/mtone-requests/README.md)与关联 Knoted Issue，识别同一能力/消费场景；重复需求补充原记录。未能查重就标明，不能声称无重复。
3. 分类：

   | 结果 | 交付 |
   |---|---|
   | 已有组件可用 | 指明实际公开组件与消费测试，不提新组件 |
   | 现有组件能组合/纯业务适配 | 说明 Knoted 的组合与状态责任，不提通用库任务，也不开上游 Issue |
   | 资料不足/尚未实验 | 列待核查资料与最小验证步骤，不发布“确定缺失”结论 |
   | 已证实通用缺口：缺能力，或既有组件需修改/扩展 | 生成下列完整提示词，存档、直接发给用户，并在上游创建或补充 Issue（步骤 6） |

4. 不用“无同名导出”代替能力判断。API 只有 items/next_cursor 时先用已有 Button 组合翻页，不能为了 Pagination 伪造 total。业务权限、API、DTO、编辑器命令不进入 mtone。判定缺口前先穷尽公开能力：props/受控值、tokens/主题、CSS 变量与应用层组合；能由此满足的属于应用适配，不算缺口、不开单。
5. 真实缺口使用下方输出契约；证据附件缺失时保留明确待补项，不能把输入断言写成亲自复现。
6. 证实缺口时在 <https://github.com/xingjianxu/mtone> 创建或补充上游 Issue。这与告知用户同等必要，缺任一项不算完成交接：
   - 先查重：`gh issue list -R xingjianxu/mtone --state all --search '关键词 in:title,body'`，打开候选核实。命中同一能力时在该 Issue 下评论补充新的消费场景与证据（复用算已完成本步骤，记录时注明“复用”），不重复开单。
   - 用英文正文（上游仓库惯用语言），只写可跨应用复用的能力、锁定版本、复现步骤与期望验收；正文不粘 Knoted 内部链接、任务卡细节、权限模型、私有正文或凭据，复现用最小公开数据。
   - 仅使用上游既有标签，按性质选择：新能力/扩展用 `enhancement`，既有组件缺陷或行为错误用 `bug`，无障碍问题用 `accessibility`；性质不明确时先用 `enhancement` 并在正文说明待定，只有确认是回归或与已发布文档/类型不一致才用 `bug`。不新增/删除上游标签，不改其仓库设置，不提 PR。
   - 修改/扩展既有组件时，必须写明当前行为、锁定版本下的最小复现、期望行为与兼容影响（旧用法是否保持），不只说“希望支持”。
   - 正文可按输出契约精简，但目标与非目标、公开能力证据、期望验收必须齐备。
   - 创建/评论失败（权限、网络、上游关闭 Issue 等）不得伪造链接：保留本地记录与提示词，如实报告失败原因并列入待补项，同时仍完成告知用户。
   - 成功后把 Issue 编号与 URL 回写到[需求记录](../../../docs/plans/knoted-v1/mtone-requests/README.md)、关联 Knoted Issue 和受影响任务卡。
   - 该 Issue 后续被关闭为不适用或已由已有能力覆盖时，同步更新本地记录状态与理由，不据上游关闭直接解除 Knoted 消费验收。

7. 记录关联任务的受影响验收与恢复条件。等待上游用技术依赖 blocked，保留 Projects 阶段；没有新增架构/权限边界不标 human-required。仅已交接不算完成。用户返回 npm 版本后核验发布、精确锁版、消费测试及正常 PR/主线/适用部署收尾，才解除相应依赖并完成任务。

## 输出契约

先给分类结论与理由；真实缺口再输出**一个完整可复制的提示词**（中文，交给用户存档）；提交给上游的 Issue 用同一内容的英文精简版，两者能力边界与验收不得冲突。以下各槽位必填，未知明确写未提供：

1. **身份与状态**：需求类型（缺能力 / 修改既有组件）、需求 ID、关联消费任务/Issue、查重结论、上游 Issue 编号与 URL（未创建时写原因，不得虚构）、存档路径；区分草稿/已交接/待发布/待消费验收/已验证。
2. **版本与证据**：实际 npm 锁定版本、资料 URL/文件/行号、复现步骤及结果；输入事实和亲测分开，缺失证据列待补。
3. **目标与非目标**：可跨应用复用的能力或需变更的组件，排除 Knoted 后端、DTO、权限及编辑器业务；修改既有组件时分开写当前行为与期望行为。
4. **公开接口建议**：现有 API、无法组合满足的理由、拟增能力分别写；props 名只是提案，由 mtone 开发者确认，兼容旧用法。
5. **状态与交互**：受控/非受控（按需）、键盘、焦点、无障碍、加载/禁用/错误/取消及生命周期；不适用项写原因。
6. **验收与交付**：可复现用例、上游测试/类型/文档/最小消费示例、实际结果、变更说明与包含修复的 npm 发布版本，不指定未经核实的上游命令。
7. **消费端恢复**：哪些任务等待、何种已发布版本/公开能力可恢复、Knoted 哪些测试与集成必须通过；master 合入不等于可消费。

提示词之外附本地下一步和未验证项。存档遵守独立 Worktree；“已交接”需要提示词实际发给用户，且上游 Issue 已存在（新建或复用既有并补充评论），只写文件或只提 Issue 都不算。

## 判定示例与常见错误

T19 仅有 next_cursor、没有 total，但 mtone 有 Button：结论是现有组件组合，游标栈留在 Knoted；输出下一页/上一页/筛选重置验收，不申请 PagedList，不造总数，也不提上游 Issue。

- “需要修改组件” → 先确认不是公开 props/tokens/主题/CSS 变量或应用层组合能解决的；确认组件本身必须变更才是缺口，同样要存档提示词、告知用户并提上游 Issue（`enhancement`/`bug`/`accessibility`），不能只在本仓库适配绕过去，也不能把应用偏好当成上游需求开单。
- “提示词已发给用户” → 交接未完成，还缺上游 Issue（或反之）。
- “master 已修，所以不用提 Issue” → 若确有同能力 Issue 则评论复用；没有就新建，不以未发布实现替代交接。

- “文档未读到” → 待核查，不是已确认缺失。
- “同事说 master 修了” → 输入事实、待发布，不跳过消费验收。
- “赶进度先写本地通用实现” → 记录技术依赖与上游交接，保留已有未合入成果，不擅自删除，也不合入替代库。
- “已有组件叫 Modal，不叫 Dialog” → 按真实 API 验证，不要求别名层。
