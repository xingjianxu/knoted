# 11 · 回收站

**依赖与所有权** 01 后由一名页面 Agent 负责 `apps/web/src/features/trash/TrashPage.tsx`、T42 回归和 /trash 视图。输入为 TrashItem、can_restore、reason 与原有游标。

## 布局和恢复流程

现有筛选、刷新、每行的恢复位置、恢复按钮均纵排；笔记很多时，一屏主要由表单占据。目标是让用户按标题、类型和删除时间找到对象，再选择恢复方式。

1. 页头「回收站」下方一行类型筛选与刷新；保留简短的 30 天清理资格提示。以 List/ListItem 显示名称、类型、上海删除时间、必要的不可恢复原因，末端仅保留「恢复…」。窄屏名称、元信息分两行，原因可换行。
2. 打开 Dialog 后明确对象；仅笔记可选择原位置或根目录。对于原位置受阻且可尝试根目录的笔记，仍允许进入对话框并选根目录。其他禁用项在行内读得出原因。对话框展示最终目的地，提交中锁定操作。
3. 成功后从各缓存移除对应类型与 ID，显示状态并更新相关视图。若随后的刷新失败，给出「刷新」入口。失败提示区分版本或关系变化与对象已清理；翻页、筛选和忙碌判定沿用现有逻辑。
4. 模拟同名不同类型记录、受阻笔记改选根目录、不可恢复的事项、连续翻页、恢复后读取失败。桌面从同一行打开确认，键盘取消回同一行；成功移除触发行后焦点落在下一行或列表标题，读屏获知成功。

**验收证据** 导出 1440 与 390px 同一组记录的列表和恢复弹窗、空筛选结果与局部失败截图，核对存在中的 30 天以上对象仍可按服务端条件尝试恢复。运行 `pnpm --filter @knoted/web exec vitest run tests/tasks/t42.test.tsx`、`pnpm exec playwright test tests/e2e/admin-layout.spec.ts`。由总负责人核对笔记、项目、事项恢复后的联动。
