## 问题与目标

在独立 Chromium 夹具中，从斜杠菜单插入「表格」并输入中文，或粘贴一行两列的 HTML 表格，均会显示表格和用户报告的告警。保存 JSON 未收到表格或单元格文字。当前锁定的 `@bixlab/mtone-blockeditor@0.2.2` 可通过 `initialContent` 和 `onChange` 传递表格。应用的适配器按 v1 白名单拒绝 `table`，Rust 校验和 OpenAPI 也只接受现有七种块。

用户从菜单插入或粘贴普通表格后，应能保存笔记，在重开、历史预览和历史恢复中看到同样的表格，并按单元格文字搜索。合并单元格和其他扩展块另行讨论。

## 方案比较

| 方案 | 用户结果 | 影响 |
| --- | --- | --- |
| 保持现有文档格式，提供显式转文本流程 | 可保存文字，原表格的行列语义会转换成文本 | 可复用现有持久化。用户需要执行转换，且重开后无法用编辑器表格操作调整行列 |
| 在现有 v1 格式新增普通表格块 | 行列、表头、列宽与受支持的行内格式可往返编辑、保存及恢复 | 扩展 Rust、OpenAPI 和前端的白名单。现有文档仍可直接使用，旧客户端无法读取含新类型的文档 |
| 新增 v2 格式版本 | 同样支持真正的表格，可为旧客户端显式提供版本差异 | 要协调笔记读取、写入、历史快照、索引、数据库版本约束和发布顺序。旧客户端仍需处理版本不兼容 |

## 推荐方案

将普通表格作为 `NoteDocument` v1 的新增块类型。以独立的 `table` 字段存放矩形行列，单元格内容复用现有 `InlineNode[]`，保留空单元格、表头行列数和列宽。允许现有五种行内标记及安全链接。编辑器的颜色、对齐等样式沿用笔记现有的持久化范围。

前端适配层把编辑器公开的 `tableContent` 转换成上述数据并双向还原。服务端校验表格至少有一行一列、每行列数一致、表头数量不超过对应维度，列宽在允许范围内。沿用整份文档 2 MiB、5000 块、8 层嵌套的限制，再根据浏览器样例为行、列和文档内单元格总数设上限。遇到含合并单元格的表格、非法链接或超出限制的内容，按对应原因提示，保留上次已保存的笔记。纯文本链接建议只出现在链接告警中。

## 影响与发布

- 当前笔记和历史均以 JSONB 保存。方案保留 `format_version = 1`，已有七种块无需重写，现有 CAS、快照版本和权限检查继续适用。历史快照无需增加版本列。
- Rust 把表格单元格按行列顺序提取为纯文本，列用制表符分隔，行用换行符分隔。全文和 RAG 分块使用现有纯文本提取及块 ID 定位，测试覆盖超过单一分块长度的表格。
- 更新 OpenAPI 及生成客户端。部署时确保 API、Worker 和 Web 均已能处理表格，再开始写入表格。旧版 Web 对 `table` 的打开路径会报错，旧版 Worker 也会拒绝含表格的文档。已产生表格文档后，常规回退需使用保留表格读取能力的版本。如必须退回旧格式，需要另行确认兼容方案。

## 验收与待确认

- 在真实浏览器验证插入表格、从剪贴板粘贴普通表格、编辑及增删行列、自动保存和手动保存。刷新后的行列、表头、列宽、空单元格、文字和受支持的行内格式应一致。
- 使用真实 API 验证历史预览、恢复、并发冲突及搜索命中。混合旧笔记块与表格的文档正常往返，旧笔记与历史兼容。
- 测试不规则行列、无效表头、无效列宽、合并单元格、非法链接、限额边界及其他未支持块。无效写入不会产生新正文或历史版本。
- 请项目维护者确认是否采用上述 v1 扩展。确认后将决定写入 ADR，再开始实现。
